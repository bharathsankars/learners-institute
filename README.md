# Learners Institute

Public website and staff administration portal for **Learners Commercial Institute**, a typewriting, shorthand and computer-skills training centre in Kottayam, Kerala.

Visitors browse the live course catalogue and submit admission enquiries. Staff sign in to a role-restricted portal to manage enquiries, students, courses and institute settings, and to convert an enquiry into an admitted student.

**Stack:** React 19 · TypeScript · Vite · TanStack Query · Node.js · Express 5 · Prisma 7 · PostgreSQL 16 · Zod · Docker

## Features

**Public website**

- Course catalogue loaded from the database (`GET /api/courses/public`), so admin edits appear on the homepage without a redeploy
- Enquiry form with client-side validation (React Hook Form + Zod); a per-submission UUID makes retries idempotent, so a flaky connection cannot create duplicate enquiries
- Rule-based "Learner Assistant" that answers questions about courses, admissions, location and contact details from the live catalogue
- Light/dark theme toggle, mobile contact bar and responsive layouts

**Administration portal** (`/admin`)

- Session-based sign-in with four roles: `SUPER_ADMIN`, `ADMIN`, `STAFF` and a restricted `RECOVERY_ADMIN`
- Dashboard with enquiry and student summaries
- Enquiries: search, filter, status workflow (New → Contacted → Closed), auto-refresh every 30 s and on window focus, and admission of an enquiry as a student
- Students: create, view and update records; admission numbers are generated by a PostgreSQL sequence
- Courses: create, edit and delete, with active/inactive status and display order controlling the public catalogue
- Settings (Super Admin only): institute contact details and admin user management
- Super Admin password recovery through a separate Recovery Admin account using time-limited, single-use codes

**Fees and payments (API)**

- Fee plans per enrollment with discounts and due dates
- Append-only payment ledger with sequential receipt numbers, idempotent submissions and balance checks
- Restricted to `SUPER_ADMIN` at the API layer
- The admin UI pages exist in `client/src/admin/pages` but the `/admin/fees` and `/admin/payments` routes currently render an "upcoming" placeholder

## Architecture

```text
┌──────────────────────┐   HTTPS + session cookie   ┌──────────────────────────┐        ┌──────────────┐
│ React 19 SPA (Vite)  │ ─────────────────────────▶ │ Express 5 REST API       │ ─────▶ │ PostgreSQL 16│
│ public site + /admin │      /api/* (JSON)         │ routes → controllers →   │ Prisma │              │
│ TanStack Query cache │ ◀───────────────────────── │ services → Prisma client │ ◀───── │              │
└──────────────────────┘                            └──────────────────────────┘        └──────────────┘
```

- **Client** (`client/`): React Router for public and admin routes, lazy-loaded admin pages, TanStack Query for server state, typed API modules in `src/api/`.
- **Server** (`server/`): layered as `routes → controllers → services`, with Zod validators for every request body and a Zod-validated environment config that fails fast on startup.
- **Database**: Prisma schema with 13 versioned SQL migrations covering users, sessions, students, courses, enrollments, fee plans, payments, enquiries, settings and recovery codes. Money is stored as integer paise to avoid floating-point rounding.
- **Deployment**: `client/vercel.json` proxies `/api/*` to a separately deployed API and rewrites all other paths to the SPA. `docker-compose.yml` runs PostgreSQL, the API and the built client locally.

## Security model

| Concern | Implementation |
|---|---|
| Passwords | bcrypt hashes; login rejects any stored value that is not a bcrypt hash |
| Sessions | 32-byte random token in an `httpOnly`, `sameSite=lax` cookie (`secure` in production); only the SHA-256 hash is stored server-side, with an 8-hour expiry |
| Authorization | Middleware enforces authenticated, Super-Admin-only and Recovery-Admin-only routes; Recovery Admins are blocked from normal admin APIs |
| Input validation | Zod schemas on every write endpoint |
| HTTP hardening | Helmet headers, `x-powered-by` disabled, CORS restricted to `CLIENT_ORIGIN`, 1 MB body limit |
| Abuse limits | Rate limit on recovery endpoints (10 requests / 15 min) |
| Financial integrity | Payment creation runs in a transaction with `SELECT … FOR UPDATE` on the fee plan, so concurrent collections cannot exceed the outstanding balance |

## Getting started

### Prerequisites

- Node.js 22 (the Dockerfiles use `node:22-alpine`)
- Docker Desktop, or a local PostgreSQL 16 instance

### 1. Start PostgreSQL

```bash
docker compose up -d postgres
```

This exposes PostgreSQL on **localhost:5433** with the development credentials defined in `docker-compose.yml`.

### 2. Configure and run the API

```bash
cd server
cat > .env <<'EOF'
DATABASE_URL=postgresql://learners:learners_dev_password@localhost:5433/learners_institute?schema=public
CLIENT_ORIGIN=http://localhost:5173
EOF

npm install          # runs `prisma generate`; DATABASE_URL must already be set
npm run prisma:deploy
npm run dev          # http://localhost:4000/api/health
```

Optional: seed the default course catalogue after a build.

```bash
npm run build && node scripts/seed-basic-courses.mjs
```

> There is no seed script for admin users. Create the first `SUPER_ADMIN` row with a bcrypt-hashed password (for example via `npm run prisma:studio`) before signing in.

### 3. Run the client

```bash
cd client
npm install
npm run dev          # http://localhost:5173
```

When the browser runs on `localhost`, the client calls `http://localhost:4000` automatically. Set `VITE_API_URL` to point elsewhere.

### Full stack with Docker Compose

```bash
docker compose up --build
```

Client on http://localhost:5173, API on http://localhost:4000. Migrations are not applied automatically; run `npm run prisma:deploy` in `server/` against the containerised database first.

## Environment variables

**server/.env**

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `DATABASE_URL` | Yes | – | PostgreSQL connection string used by the API and Prisma |
| `DIRECT_URL` | No | `DATABASE_URL` | Direct connection for migrations when `DATABASE_URL` points at a pooler |
| `CLIENT_ORIGIN` | No | `http://localhost:5173` | Allowed CORS origin |
| `PORT` | No | `4000` | API port |
| `NODE_ENV` | No | `development` | `production` enables secure cookies |

**client/.env**

| Variable | Required | Purpose |
|---|---|---|
| `VITE_API_URL` | No | API base URL. Empty in production so requests go through the Vercel `/api` rewrite |

## Testing

Both packages use the built-in Node.js test runner, with no extra test framework.

- **Server** (`server/tests/`): enquiry validation and retry deduplication, payment rules and financial access control, course logic and admin route access. Database calls are mocked; `enquiries.live.mjs` is an opt-in check against a running database.
- **Client** (`client/tests/`): pure-function tests for dashboard, enquiry, student and course utilities and the Learner Assistant responses.

```bash
cd server && npm test
cd client && node --experimental-strip-types --test tests/*.test.ts
```

## Technical decisions

- **Server-side sessions instead of JWTs.** Logout and account deactivation take effect immediately because each request checks a stored session hash and `isActive`.
- **Idempotency keys on public and financial writes.** Enquiries and payments carry a client-generated `requestId`; an identical retry returns the original record, and a reused ID with different data is rejected.
- **Integer currency.** Fees and payments are stored in paise (`Int`), never as floats.
- **Append-only payments.** Corrections, voids and refunds are deliberately out of scope rather than implemented as destructive edits.
- **Database-generated admission numbers.** A PostgreSQL sequence avoids race conditions when two staff admit students at the same time.
